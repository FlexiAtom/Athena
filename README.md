# Athena

在**用 AI 维护软件**的过程中，我遇到了一些问题——

新的需求与想法、正在进行的验证与修改、已经结束的工作……在过去，这些会留痕在 QQ 和 GitHub（仅举例，不限于这两个）上；而对于 AI，这些只活在对话历史里。但历史会压缩、对话会丢失、Agent会更换、溯源无处可查……

**为了解决这些问题，我提出——一种以提示词工程为原理、面向 AI 的工作状态机**：有哪些项目、各自处在提案 / 草案 / 方案、池 / 进行中 / 结束 / 社区互助……状态即目录、文档即记忆，推进要反证、要剪枝、要留痕。

![license](https://img.shields.io/badge/license-AGPL--3.0-blue)

Athena 由 AI 驱动。**作为人，你只需两步**：编译它、在每个项目里跑一次 `init`；此后协议的一切推进都由 AI 读取项目根的 [`AGENTS.md`](./AGENTS.md) 来执行。命令一览、反证留痕、状态根结构等细节都写在 `AGENTS.md`（给 AI 读的入口）和 [`athena.md`](./athena.md)（完整设计）里，本 README 不重复。唯一例外是下面「核心模型：两条正交的轴」——它是理解整个模型的前提，人也要懂，故原样摘来放在此处。

## 现状：滚动更新，作者本人就是唯一用户

Athena **没有发布周期，也不承诺版本兼容**。我自己天天用它，随时可能发现 bug、随时修、随时加功能——你今天看到的命令签名、入口文本、模板，下一个提交就可能已经变了（这是常态，不是事故）。所以别在这里找 "upgrade 指引"，要跟就盯提交。

还有一件事容易被忽略：**clone 仓库只拿到代码，协议的另一半在状态根 `~/.Athena` 里**——模板 overlay、术语表、全局坑、人话台账、配置全在那儿，而它们**不随仓库分发**（那是工作状态，不是源码）。想要开箱即用，来找我拿我的 `~/.Athena`；拿到之后请按私有资料对待（里面含我各个项目的真实过程记录），并且在你自己机器上仍需对每个项目跑一次 `athena init <proj>` 建骨架。缺了这半份，工具照样能跑，只是空有骨架、没有积累——这大概就是最容易坑到人的一点。

因为「不设防」（见下文立场），bug 的表现通常不是崩溃，而是**静默留下一条不对的记录**。两条兜底：出状况先跑 `athena onerror` 看处置手册；状态根本身是个 git 仓库，每一次写入都有提交在身后，`git -C ~/.Athena log` 能看、能回滚。**数据可回滚，比版本号有用**——这也是这套东西敢滚动更新的原因。

一句话预期管理：适合个人 + 自己那台机器 + 愿意跟着改的人；不适合你指望它不动，也不适合团队里当共享基建。

别把"它是什么"和"推到哪一步"搞混。以下两表原样摘自 [`athena.md`](./athena.md)：

**轴一 · 文档类型（内容层级，写在文档自己身上）**

| 词 | 定义 | 说明 |
|---|---|---|
| **提案** | 我有个想法 | 只要说清动机、目标、约束、为什么值得做 |
| **草案** | 我打个草稿，这东西怎么实现 | 回答"怎么做"——技术路径、模块划分、关键决策 |
| **方案** | 我可以按照这个方案实施 | 回答"照着做就能成"——可执行到步骤级、有验收标准 |

**轴二 · 推进状态（位置，由目录表达）**

| 词 | 定义 | 目录 |
|---|---|---|
| **池** | 未推进的提案 | `pool/` |
| **进行中** | 我正在推进的提案/草案/方案 | `working/` |
| **结束** | 已经完成 | `finished/`（`status: done`） |
| **冻结** | 已经毙了 | `finished/`（`status: frozen`） |
| **社区互助** | 字面意思：放出去请社区帮忙处理 | `community/` |

一句话：**目录回答"推到哪一步"，文档自己回答"它是什么"**——两者正交。一个工作项从提案写到方案是**在同一文件里改 `kind`**（轴一，不挪目录）；从池推到结束才是**移动文件**（轴二）。

## 谁在开车：AI 是主体

Athena 是"AI 驱动"的状态机，**AI 是主体，不是被审查的对象**：每一次目录转换、每一条剪枝、每一回记忆修订，动手的都是 AI；人是方向提供者与决策确认者。所以正确表述不是"Athena **允许** AI 读写状态根"（那仍是恩赐与防守的姿态），而是——**AI 天然拥有对 `~/.Athena/` 的读写权，这是它作为驱动者的前提。** 若 AI 不能直接改状态库，它就成了每步都要人代劳的提线木偶，那是"人驱动"不是"AI 驱动"。

正因如此，CLI 只是给主体的**脚手架**，不是**镣铐**。这句立场逐字引自 [`AGENTS.md`](./AGENTS.md)：

> **Athena 不阻止，只记录与提示**（§1.3 不设防）。CLI 是脚手架不是镣铐；靠说服生效，不靠强制。若哪天要靠"拦住 AI"才能维持流程，那是协议文本没写好——去改协议，不是加固 CLI。
>
> **"不设防"仅是流程层**。不可逆 / 破坏性 / 对外动作（真实 mutation、签名、发布、push 等）仍受红线约束：须调用方**明确授权**（禁忌 7）；全量审查通过也不能替代授权。

给人的一句话：别指望这套工具"看住" AI，也不必要——它的约束对象是 AI 的默认行为，不是人的意志；**人绕过协议是权利，不是 bug**。你要做的是搭好它、把 `AGENTS.md` 交到 AI 手里，然后让 AI 去开车。

## 编译

```bash
cargo build --release
# 二进制在 target/release/athena
```

## 初始化

```bash
athena init <project>
```

在状态根 `~/.Athena` 实例化项目骨架，并把协议入口 `AGENTS.md` 复制到当前目录。装好这一步，剩下的交给 AI。
